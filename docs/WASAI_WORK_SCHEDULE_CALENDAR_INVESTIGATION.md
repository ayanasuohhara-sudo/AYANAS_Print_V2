## 1. 目的の整理

| 要件 | 意味 |
|------|------|
| 和裁士を選ぶと月間カレンダー | 人単位の負荷可視化 |
| 出庫済み・返却予定日・品目・枚数 | 実出庫（App74）の予定日軸表示 |
| 月間処理可能 / 予定 / 追加可能 | キャパシティ判断の KPI |
| 未出庫の予定登録 | 実出庫前の「これから渡す／渡す予定」 |
| 前月・翌月 | 月ナビ |
| 将来スマホ入力 | 本人が予定を入れる前提の権限・データ分離 |

核心は **「今その和裁士の手元・予定に何枚あるか」を見て、次に何枚渡せるか決めること**。

## 3. 状態の区別（出庫済 / 返却済 / 未出庫予定）

| 区分 | 定義（推奨） | データソース | カレンダー色の例 |
|------|--------------|--------------|------------------|
| **出庫済・手元** | `outbound_status=出庫確定` かつ行が未入庫（`line_status` が空 or `出庫中`） | App74 | 青系（負荷中） |
| **返却済** | 同上ヘッダーで行が `入庫済` 以降（検品OK・計上済等含む）。再加工は別扱い可 | App74（+ 任意で App78 証跡） | 灰系（完了） |
| **未出庫予定** | まだ App74 に出庫確定がないが、渡す／返ってくる見込み | **現状アプリに存在しない** → 新規予定レコードが必要 | 橙系（予定） |

**表示軸の推奨**

- 主軸: **返却予定日**（App74 `return_date` / 予定の `planned_return_date`）
- 補助: 出庫日（`日ship_date` / `planned_ship_date`）をツールチップまたは別トグル
- セル内容: 品目（`processing_summary` または予定の品目）、枚数（`eligible_line_coun` または予定枚数）、管理番号

**再加工**

- `line_status=再加工` は支払対象外だが「手元に戻っている／再出庫待ち」の可能性がある。KPI の「予定枚数」に含めるかは運用確認事項（初期案: **手元負荷には含め、完了には含めない**）。

## 4. 二重計上を防ぐ方法

### 4.1 やってはいけないこと

- App16「和裁士作業中」件数 **と** App74 出庫中件数を **足す**（同一 manage_no の二重）
- 予定レコードを出庫後も「予定」のまま残し、App74 と **両方を予定枚数に加算**
- App78 入庫行と App74 `inbound_date` 入り行を別々に完了件数として加算

### 4.2 推奨ルール（単一の正本）

| 観点 | 正本 | 補足 |
|------|------|------|
| 実出庫・手元・実返却 | **App74 明細** | App16 は工程の結果表示。集計キーに使わない |
| 未出庫の約束 | **予定アプリ（新規）のみ** | App74 下書きに載せない |
| 入庫確定イベント | App78 | カレンダー集計の主キーにしない |

**リンク規則**

1. 予定レコードに任意で `manage_no`（または仮キー）を持たせる  
2. App74 出庫確定時（またはカレンダー同期ジョブ）に同一 `manage_no` + `wasai_code` を検索  
3. ヒットしたら予定を **`linked`（出庫済リンク）** にし、KPI の「予定」からは除外、表示は App74 側に一本化  
4. `manage_no` 未設定の「枠だけ予定」（枚数だけ押さえる）は出庫時に手動消化 or 出庫 UI から紐付け

**月間 KPI 計算（推奨式）**

```
月間処理可能枚数 C  = App73.monthly_capacity（未設定時は手動入力 or 空＝判定不可）
予定枚数 P         = Σ(表示月の返却予定日に属する)
                     ・App74: 出庫確定かつ（未入庫 or 当月入庫）の枚数
                     ・予定App: status=予定 かつ 未リンク の枚数
追加可能枚数 A     = max(0, C − P)
```

- 「返却予定日が当月」で揃えると、出庫日ベースと混在しない  
- 返却予定が空の App74 は出庫日フォールバック（現行 JS と同じ）

## 5. 実現方式の比較

### 案A — 既存 App74 のみで実現

| 項目 | 評価 |
|------|------|
| 出庫済み表示 | ◎ データそのまま |
| 未出庫予定 | △ `outbound_status=下書き` やダミー明細で無理やり → 出庫 JS・支払・入庫と衝突しやすい |
| KPI | ○ JS で集計可能だがマスタにキャパなし |
| スマホ本人入力 | ✕ 出庫アプリ権限を本人に渡すのは危険（誤出庫・金額スナップショット） |
| 改修影響 | 出庫・検品・入庫・支払の広い回帰 |

**結論**: 閲覧カレンダーの土台には使えるが、**予定登録とスマホ入力には不適**。

### 案B — App73 / App16 拡張のみ

| 項目 | 評価 |
|------|------|
| App73 にキャパ追加 | ◎ 必要 |
| App16 に予定日 | ✕ 和裁士紐付けがなく、未出庫の「誰に渡すか」を表現しづらい |
| 二重計上 | App16 と App74 の同期ズレで破綻しやすい |

**結論**: マスタ拡張は有用だが、**予定の器としては不十分**。

### 案C — 新規「予定管理アプリ」+ カレンダーホスト（推奨）

| 項目 | 評価 |
|------|------|
| 出庫済み | App74 を参照表示（書込しない） |
| 未出庫予定 | 新規 App に POST。出庫業務と分離 |
| 二重計上 | `manage_no` リンク + status で制御しやすい |
| スマホ | 予定 App のみモバイル権限。出庫・支払は事務所のみ |
| UI | App89 / App94 と同様、ホスト App 一覧をカレンダーで置換する JS |
| コスト | アプリ1つ追加 + JS + App73 に数フィールド |

**結論**: 要件 1〜6 を満たし、将来の本人入力にも耐える。**推奨**。

### 案D — 既存 App74 下書き + 別カレンダー JS（折衷）

短期で「予定も下書きで入れる」案。出庫確定フローと混線し、二重計上・権限分離が弱い。**非推奨**（移行期の暫定にも慎重に）。

## 9. 結論

| 項目 | 内容 |
|------|------|
| 出庫済みの正本 | **App74**（`出庫確定` + 明細 `line_status`） |
| 返却済みの正本 | App74 明細の入庫以降（App78 は入庫イベント） |

| 推奨 | **新規予定管理 + カレンダーホスト JS + App73 に月間キャパ**。App74/78/16 の出庫入庫フローは触らず参照する |
