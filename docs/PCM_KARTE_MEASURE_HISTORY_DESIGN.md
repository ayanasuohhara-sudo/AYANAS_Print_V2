## 1. App96 寸法履歴 — フィールド構成

### 1.1 追加対象（案）

単一サブテーブル `measure_history`（ラベル: **寸法履歴**）を App96 に追加する。

| コード | ラベル | 種別 | 必須 | 説明 |
|--------|--------|------|------|------|
| `measure_history` | 寸法履歴 | SUBTABLE | — | 履歴行の容器 |
| └ `measured_at` | 採寸日 | DATE | ○ | 採寸または仕上がり確定日 |
| └ `measure_kind` | 寸法区分 | DROP_DOWN | ○ | `身体寸法` / `仕上がり寸法` |
| └ `garment_type` | 対象 | DROP_DOWN | ○ | 下記 §1.2 |
| └ `measure_label` | 寸法名称 | 文字列1行 | — | 例「初回採寸」「訪問着仕立2026秋」 |
| └ `is_current` | 現行 | CHECK_BOX | — | 値 `現行` のみ。同一区分×対象で原則1行 |
| └ `manage_no` | 関連管理番号 | 文字列1行 | — | 仕上がりを特定受注に紐付ける場合 |
| └ `height_cm` | 身長(cm) | NUMBER | — | 身体寸法向け |
| └ `mitake_cm` | 身丈(cm) | NUMBER | — | 仕上がり中心 |
| └ `yuki_cm` | 裄(cm) | NUMBER | — | 身体／仕上がり共通で使用可 |
| └ `katahaba_cm` | 肩幅(cm) | NUMBER | — | |
| └ `sodetable_cm` | 袖丈(cm) | NUMBER | — | |
| └ `sodehaba_cm` | 袖幅(cm) | NUMBER | — | 仕上がり |
| └ `maehaba_cm` | 前幅(cm) | NUMBER | — | 仕上がり |
| └ `ushirohaba_cm` | 後幅(cm) | NUMBER | — | 仕上がり |
| └ `suso_cm` | 裾回り(cm) | NUMBER | — | 仕上がり |
| └ `eri_cm` | 衿(cm) | NUMBER | — | 任意 |
| └ `bust_cm` | バスト/胸囲(cm) | NUMBER | — | 身体 |
| └ `waist_cm` | ウエスト(cm) | NUMBER | — | 身体 |
| └ `hip_cm` | ヒップ(cm) | NUMBER | — | 身体 |
| └ `measure_note` | 備考 | 複数行 | — | 採寸者・特記 |

単位はすべて **cm**。未使用列は空でよい（長襦袢で使わない項目など）。

### 1.2 対象（`garment_type`）選択肢

| 値 | 想定 `measure_kind` |
|----|---------------------|
| 身体 | 身体寸法 |
| 長着 | 仕上がり寸法 |
| 長襦袢 | 仕上がり寸法 |
| 羽織 | 仕上がり寸法 |
| コート | 仕上がり寸法 |
| 袴 | 仕上がり寸法（将来） |
| その他 | どちらでも可 |

### 1.3 身体寸法と仕上がり寸法の区別ルール

| 区分 | 意味 | 典型列 |
|------|------|--------|
| **身体寸法** | 人の体の採寸。着物種別をまたいで再利用 | 身長・バスト・ウエスト・ヒップ・肩幅・体の裄 等 |
| **仕上がり寸法** | その着物の仕上がり／仕立指示 | 身丈・裄・袖丈・袖幅・前幅・後幅・裾回り 等 |

- UI上は区分で入力欄を出し分け（不要列は薄く／非表示）
- バリデーション（JS）:
  - `身体寸法` → `garment_type` は原則 `身体`
  - `仕上がり寸法` → `garment_type` は着物種（長着等）。`身体` 禁止
- **過去行は削除せず残す。** 修正は「現行フラグを外し、新行を追加」が基本

### 1.4 現行セットの扱い

- `is_current` = `現行` の行を、区分×対象ごとに最新表示
- 新行保存時JS: 同区分・同対象の他行から `現行` を外す（履歴行自体は残す）
- レコード先頭に「現行寸法サマリ」（JS描画、フィールドではない）を表示

### 1.5 レイアウト案（App96 詳細）

```text
[基本情報] 氏名・かな・電話・会員…
[現行寸法サマリ] ← JS（身体 / 長着 / 長襦袢 / 羽織 / コート）
[寸法履歴]       ← サブテーブル（新しい行が上）
[利用履歴]       ← pcm_order_history 拡張パネル
[メモ]
```

編集画面: サブテーブルを直接編集。詳細画面: 読取＋大きめカード。

### 1.6 新規アプリは不要

寸法専用アプリは作らない。App96 サブテーブルで複数種・複数世代を保持できる。

## 5. A550 未紐付け70件 — 照合と更新方式

### 5.1 実測サマリー（2026-11-16・読取のみ）

| 指標 | 件数 |
|------|------|
| A550 受注 | 134 |
| `personal_customer_id` あり | 64 |
| **未紐付け** | **70** |
| 未紐付けユニーク氏名 | 41（グループ47※空・表記ゆれ含む） |
| 氏名一致・候補1件 | **24** |
| 氏名一致・候補複数 | 0 |
| かなのみ一致 | 0 |
| **候補なし** | **46** |
| 同氏名で既に別PID紐付けあり | 2 |
| App96 | 71 |

※詳細: `A550_UNMATCHED_CANDIDATES.md` / `a550_unmatched_candidates.json`

例（候補1件・要確認）: 佐保山素子×9 → `P000044`、山村若瑞×2 → `P000034`、松村美保×2 → `P000042`  
候補なし例: 平城京天平行列実行委員会×5、田上早百合×3、山口母×2 等（団体・家族表記・未登録個人）

### 5.2 原則

1. **氏名だけで自動更新しない**
2. 候補は提示のみ。スタッフが確認してから更新
3. 衝突（同氏名で別PIDが既に紐付）は手動判断
4. 候補なしは「App96新規作成 → 紐付け」または「紐付け保留」

### 5.3 推奨ワークフロー（実装は後日）

```text
1. 照合レポート生成（今回の probe と同様・読取）
2. 確認UI または CSV:
     manage_no / 受注日 / client_name / 候補PID / 候補氏名 / grade / 判定(承認|却下|新規PCM|保留)
3. 承認行のみ App16.personal_customer_id を一括PUT（revision付き・ドライラン必須）
4. 結果ログ保存。App96 last_order_date 等の再計算は任意バッチ
```

| grade | 扱い |
|-------|------|
| `exact_name_1` | 確認リストの主対象。1件ずつまたはグループ承認 |
| `exact_name_multi` | 必ず個別確認（今回0件） |
| `kana_only_1` | かな一致のみ。電話等の追加確認を推奨 |
| `none` | PCM新規 or 保留。団体名は請求・備考運用を別検討 |
| 衝突あり | 既存PIDと突合し、誤統合を防ぐ |

**自動適用スクリプトは提供しない**（または `--approve-file` 必須）。

### 5.4 確認UI案（軽量）

- 置き場所: App96 一覧の管理者向けパネル、または社内用一時ページ
- 表示: 氏名グループ単位（例 佐保山素子の9件をまとめて承認）
- 操作: 候補PID選択 / 新規PCM作成リンク / スキップ
- 権限: 店舗一般は閲覧、更新は責任者
