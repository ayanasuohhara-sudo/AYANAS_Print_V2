# 店舗A550 受注表・納品書の印刷単位 — 現状調査とレイアウト案

- **作成**: 2026-11-02（Asia/Tokyo）
- **範囲**: 調査・レイアウト案のみ。**コード実装・本番反映は未実施（別途承認）**
- **制約**: 法人用受注表・App19法人納品処理は変更しない

---

## 0. 結論（要約）

| 帳票 | 印刷単位（方針） | 現状 | ギャップ |
|------|------------------|------|----------|
| **店舗受注表** | App16 の 1 レコード = 1 枚（着物1点） | App16 に「受注明細表」「海外用受注表」「受注票」あり。入金表示なし | A550専用レイアウト＋App97入金状態の取得が未実装 |
| **店舗納品書** | 同一お客様の選択商品を 1 枚にまとめ（部分可） | App19 で複数 `manage_no` を明細に載せ、明細分だけ App16 同期 | PCM拘束なし／入金額・残額なし／ヘッダが店舗顧客(A550)表記 |

**推奨実装方針（承認後）**

1. **店舗受注表**: 既存 Print SDK に `store_order`（仮）を追加。App16 レコード画面から印刷。データは 1 レコード＋App97 残高照会。
2. **店舗納品書**: 既存 App19 納品書をベースに A550 分岐テンプレ（または `recipientMode: 'store'`）。明細は選択商品のみ。フッタに合計／入金／残。法人テンプレは触らない。
3. **選択・同期**: App19 既存の「明細 manage_no のみ同期」を維持。PCM 同一拘束を読取時に追加。二重 `delivery_no` は現行 warn を維持。

## 1. App16 の 1 レコードから店舗受注表を印刷する方法

### 1.1 現状

印刷は **AYANAS Print プラグイン**（`js/desktop.js` → `Record` → `Preview` → template）。

| reportType | ボタン（App16） | 単位 | バーコード | 入金 |
|------------|-----------------|------|------------|------|
| `order`（受注票） | 既定登録あり・App16ボタン未露出の可能性 | 1レコード | manage_no | なし |
| `order_detail`（受注明細表） | **受注明細表** | 1レコード・左右2面 | manage_no CODE39 表示 | なし |
| `overseas_order`（海外用受注表） | **海外用受注表** | 1レコード | manage_no | なし |

`order_detail` はすでに **App16 の 1 レコード＝1 帳票**（着物1点＝manage_no 1つ）で、管理番号バーコード・着物種類・加工内容・納期・顧客／お客様名を表示する。

```text
App16 詳細画面
  → 「受注明細表」クリック
  → Record.getOrderData(record)（当該1件）
  → OrderDetailTemplate（左右コピー）
```

### 1.2 店舗受注表への当てはめ（案）

| 案 | 内容 | 評価 |
|----|------|------|
| **A. 新 reportType `store_order`** | A550 のときだけボタン表示。法人は従来ボタンのまま | **推奨**（法人非変更） |
| B. 既存 `order_detail` を拡張 | A550 時だけ入金欄を足す | 法人・一般にも影響しうる |
| C. App92 から印刷 | 在庫画面から個別印刷 | 作業現場向きだが App16正本から離れる |

**推奨 A の流れ**

1. `layout.js` に `store_order` 登録（App16、barcode=`manage_no`、表示 ON）
2. `desktop.js` で `customer_code === 'A550'` のときだけ「店舗受注表」ボタン
3. `Record.getStoreOrderData`（仮）: 既存 order 抽出＋App97 残高
4. テンプレ `js/templates/store_order.js`（作業・保管・引き取り用の単票）

法人用 `order` / `order_detail` / `overseas_order` は変更しない。

## 2. App97 の入金状況を印刷時に取得する方法

### 2.1 正本ロジック（既存）

App97 S1（変更せず参照）:

```text
billedInclusive = round(Σ App16.detail_table.amount × 1.1)  // 受注（manage_no）単位
paid            = Σ App97 有効明細の allocated_amount（当該 order_record_id）
balance         = billedInclusive - paid
state           = 未入金 | 一部入金 | 入金済 | 過剰入金
```

実装: `store_payment_engine.getOrderBalance` / `CAYANAS_StorePickup_Api` / `loadByBarcode`

### 2.2 印刷時の取得案

印刷プレビューはブラウザ上の kintone セッションで動くため、**プレビュー直前に REST GET** が可能。

```text
印刷クリック
  → App16 レコード確定（$id, manage_no, personal_customer_id, detail_table）
  → App97: personal_customer_id で入金レコード取得
     （既存 buildPaymentsByCustomerQuery）
  → getOrderBalance(order, payments) → state / paid / balance
  → テンプレへ header.payment_state 等を渡す
```

| 論点 | 方針案 |
|------|--------|
| プラグインから App97 参照 | Print プラグイン内に薄い adapter、または既存 `store_payment_engine` を App16 にも読込（A550時のみ） |
| PCM 未連携 | 「入金状況: 不明（PCM未設定）」と印字し、ブロックしない |
| オフライン／権限 | 取得失敗時は「取得失敗」印字＋コンソール。印刷自体は続行可 |

**印刷パスに入金を載せるのは現状ゼロ**（請求書 App35 の繰越のみ）。店舗受注表・納品書は新規。

## 3. 複数点の入金を商品単位で正しく表示する方法

### 3.1 データモデル上の単位

| 単位 | 意味 |
|------|------|
| App16 レコード | 着物1点（manage_no）＝請求・入金充当の最小単位（S1） |
| App97 明細行 | `order_record_id` に対する `allocated_amount` |
| App19 納品書 | 複数 manage_no を 1 枚に束ねる（選択集合） |

### 3.2 表示ルール（案）

**店舗受注表（1点）**

- その受注の `state` / 税込請求 / 入金済額 / 残額 を1ブロック表示

**店舗納品書（複数点）**

| 行 | 表示 |
|----|------|
| 明細各行 | 管理番号・品名・加工・金額（税抜）＋任意で行ごとの入金状態 |
| フッタ | 税込合計（選択分）／入金額合計（選択分の paid 合計）／未入金残（選択分の balance 合計） |

計算:

```text
for each manage_no on slip:
  bal_i = getOrderBalance(order_i, payments_of_pcm)
sum_billed = Σ bal_i.billedInclusive
sum_paid   = Σ bal_i.paid
sum_balance= Σ bal_i.balance
```

**注意**: 同一 PCM の「納品書に載せていない他商品」の入金はフッタに含めない（選択集合のみ）。  
一括入金で複数受注に充当された場合も、S1 は受注単位充当のため商品単位表示と整合する。

## 4. App19 で同一 PCM 顧客の商品だけをまとめる方法

### 4.1 現状

`barcode_delivery.js`:

1. バーコード → App16 `manage_no` 検索
2. 当該受注の `detail_table` 全行を `delivery_detail` に追加
3. ヘッダ `customer_code` / `customer_name` が空なら最初の受注からコピー
4. **`personal_customer_id` は見ていない**
5. A550 同士なら別お客様（別 PCM）でも同一納品書に混在しうる（`client_name` が明細に出るだけ）

### 4.2 追加すべきガード（案・実装は承認後）

読取時:

```text
scan → App16 取得
if header 未設定:
  セット customer_code, （推奨）personal_customer_id スナップショット
else:
  if order.personal_customer_id !== header.pcm → 拒否
  if order.customer_code !== 'A550' → 店舗帳票では拒否（法人は従来経路）
```

| 案 | 内容 |
|----|------|
| **P1** | App19 に `personal_customer_id`（または非表示スナップショット）を保持し、読取都度照合 | **推奨** |
| P2 | 明細の `client_name` 一致のみ | PCM 未連携・同姓で不十分 |
| P3 | 印刷時だけ警告 | 作成時点の混入を防げない |

法人経路（`customer_code ≠ A550`）の読取・同期は変更しない。

## 5. 一部納品時の App16 更新と App92 在庫の整合

### 5.1 現状（すでに方針と一致）

`delivery_complete_sync.collectManageNos` → **納品書明細にある manage_no のみ** PUT。

```text
お客様が着物3点保有、うち2点だけ納品書作成
  → 2点: delivery_no 付与、条件充足なら 引き取り待ち
  → 1点: delivery_status 変更なし（未納品のまま等）
```

App92:

- スケジュール除外: `納品済` **または** `delivery_no` 非空
- 引き取り待ち在庫: 完了∧店舗∧(引き取り待ち|納品待ち互換)∧delivery_no

よって **納品書に載せた点だけ** 在庫／除外に乗り、未掲載点は従来どおりスケジュール側に残る。

### 5.2 確認事項（運用）

| ケース | 期待 |
|--------|------|
| 2/3 点だけ納品書 | 2点のみ delivery_no／引き取り待ち。1点は未同期 |
| 残り1点を後日別納品書 | 新 `delivery_no` でその1点だけ更新。既存2点は別番号のため **warn（更新しない）**＝正しい |
| 納品書から行削除 | App16 は自動ロールバックしない（訂正は運用手順書） |

追加実装は「整合ロジックの新設」より、**店舗UIでの PCM 拘束と印刷入金欄**が主。同期ロジックは現状で部分納品に耐えている。

## 6. 納品書を複数回発行した場合の重複防止

### 6.1 現状

| 仕組み | 内容 |
|--------|------|
| App19 `delivery_no` | 初回保存時 `N{yyyymmdd}-{recordId}` 採番 |
| App16 側 | 既に別 `delivery_no` がある manage_no は `warn`（PUTしない） |
| 同一番号の再保存 | 状態・日付が同じなら `already_applied` skip |
| 納品済 | skip |

### 6.2 評価と案

- **商品単位の二重紐付け防止は既存で有効**（別納品書番号での上書き防止）。
- 不足しうる点:
  - 同一 App19 レコードの再印刷は何回でも可（番号は1つ）→ 問題なし
  - 「同じ商品セットを新規レコードでもう一度作る」→ 2点目以降は warn。運用で十分なら追加不要
  - 任意強化: 読取時に既に `delivery_no` がある商品を警告表示（作成前ガード）

## 7. 既存法人帳票との分離方法

| 層 | 分離方法 |
|----|----------|
| 印刷ボタン | App16: A550 のみ「店舗受注表」。法人は従来ボタン |
| 納品書テンプレ | `customer_code==='A550'` または新ボタン「店舗納品書」で store レイアウト。法人は `delivery` / `delivery_matsuba` 維持 |
| 同期 | 既存 `isStoreCustomer` / `isCorporateCustomer` 分岐を維持（法人は location+delivery=納品済） |
| 入金 | App97 は A550+PCM のみ。法人帳票に App97 を混ぜない |
| 受注表文言 | 店舗＝作業・保管・引き取り用。法人＝従来受注票／明細表 |
