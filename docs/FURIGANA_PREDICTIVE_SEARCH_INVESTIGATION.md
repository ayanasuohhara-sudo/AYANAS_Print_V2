# お客様名ふりがな予測検索 — 調査報告（承認前・本番未変更）

- **作成**: 2026-11-03（Asia/Tokyo）
- **状態**: **調査のみ**。App16/8/96 のフィールド追加・本番JS反映・過去データの一括更新は**未実施**（承認後）
- **目的**: 法人顧客からの電話問い合わせで、漢字不明のお客様名をふりがなから App16 受注履歴へ辿れるようにする

例: 「やまもときよこ様の訪問着はどうなっていますか？」  
→ 法人顧客コード ＋ お客様名ふりがな ＋ 着物種類 で App16 を検索

---

## 結論（先に）

| 判定 | 内容 |
|------|------|
| **標準検索だけでは不足** | App16 の `client_name` は漢字スナップショットのみ。ひらがな `like "やまもと"` は **0件**（検証済）。漢字 `山本` は 36件ヒット |
| **App96 のふりがなは法人問い合わせの本命ではない** | App96 は **A550（店舗）個人顧客**専用。法人受注 3,206件のお客様名とは別系統 |
| **追加が必要** | App16 に **お客様名ふりがな**（案: `client_name_kana`）を追加し、新規受注時に確認入力。過去分は**自動確定しない** |
| **検索UI** | 既存 **App88 受注検索**を拡張するのが最短（App16 正本は壊さない）。予測候補はカスタムJS必須 |

本番変更は本報告の承認後に進める。

## 2. 追加が必要なフィールド

### 2.1 推奨（最小・既存を壊しにくい）

**App16 に追加**

| コード（案） | ラベル | 型 | 必須 | 説明 |
|--------------|--------|-----|------|------|
| `client_name_kana` | お客様名ふりがな | 文字列（1行） | なし | 受注時点の読みスナップショット。検索用 |
| `client_name_kana_status`（任意） | ふりがな確認状態 | ドロップダウン | なし | 例: `確認済` / `未確認` / `不明`。過去自動候補は `未確認` |

- **App8 には追加しない**（法人マスタに個人ふりがなを載せると責務が混ざる）
- **App96 を法人お客様の正本にしない**（A550 専用を維持。混同禁止）
- 同姓同名を ID 統合しない。検索は「候補表示」まで。同一人物判定は人が行う

### 2.2 やらない／後回し

| 案 | 判定 |
|----|------|
| 法人向け「個人マスタ」新アプリ | 価値はあるがスコープ大。まず App16 スナップショットで問い合わせ検索を満たす |
| App16 に `personal_customer_name` 再追加 | 既存方針どおり不要（氏名表示は `client_name`） |
| 漢字→かなの一括自動確定 | **禁止**（誤読が検索事故になる） |

### 2.3 標準検索で足りる部分／カスタムが必要な部分

| 要件 | 標準 | カスタム |
|------|------|----------|
| 顧客コード一致・管理番号一致・日付範囲・ドロップダウン | ○ | — |
| お客様名漢字の部分一致 | ○（`like`）／App88 既存 | — |
| ひらがな／カタカナ／全半角／空白の吸収 | × | **必須**（正規化ユーティリティ） |
| 入力途中の候補表示 | × | **必須**（debounce typeahead） |
| 同音異字の並列候補 | × | **必須**（かな一致で複数漢字を列挙） |
| 大量時の応答 | 3千件規模なら `like`＋顧客コード絞りで実用可 | 将来はかな正規化キー列 or 外部索引を検討 |

## 3. 過去データのふりがな対応方法

**方針: 自動変換だけで確定しない。未確認として扱う。**

| フェーズ | 内容 | 本番更新 |
|----------|------|----------|
| A. フィールド追加のみ | `client_name_kana`（＋任意で status）を空で追加 | 承認後 |
| B. 候補生成（オフライン／プレビュー） | 漢字→かな辞書等で**候補CSV**を作成。App16 はまだ書かない | 書込なし可 |
| C. スタッフ確認入力 | 問い合わせ対応時・新規受注時に確定。`確認済` へ | 1件ずつ |
| D. 任意の段階的バックフィル | 頻出お客様名のみ候補提示UIで確認して保存 | 承認＋手順書後 |

A550 かつ `personal_customer_id` あり（現状11件）は、App96 の `customer_kana` を**候補として表示**してよいが、App16 へコピー確定はスタッフ確認後。

法人過去 3,200件超を一括 PUT しない。

## 4. 予測検索画面の構成（案）

**置き場所: App88（受注検索）を拡張**（App16 一覧を汚さず、正本更新もしない）

```
[法人顧客コード] [法人顧客名（参考・like）]
[お客様名ふりがな] ← 予測入力（正規化: ひらがな寄せ・カナ→ひら・全半角・空白除去）
[お客様名（漢字・任意）]
[着物種類] [管理番号] [受注日From-To] [納品状態]
[検索]

候補ドロップダウン（入力中）:
  やまもと きよこ  → 山本清子 / 山本きよこ / 山本京子 …（かな一致の既存 client_name）
  件数・最終受注日・顧客コード付き

結果テーブル:
  顧客コード | 顧客名 | お客様名 | ふりがな | 着物種類 | 管理番号 | 受注日 | 工程 | 納品状態
  → 管理番号クリックで App16 詳細
```

検索クエリ案（カスタム側で正規化キーを持つ場合）:

1. `customer_code` があれば `=` で先に絞る（必須推奨・法人問い合わせ時）
2. `client_name_kana like`（正規化後）＋任意で `kimono_type like`
3. ふりがな未登録レコードは、過渡期のみ漢字 `client_name like` を併用（ヒット品質は劣る）

正規化ルール（案）: NFKC → カタカナをひらがなへ → 長音・中点・空白除去 → 小書き統一（任意）。

## 7. 想定リスク

| リスク | 影響 | 緩和 |
|--------|------|------|
| 漢字自動よみの誤読を確定する | 検索漏れ・誤ヒット | 未確認ステータス、一括確定禁止 |
| 同姓同名の同一人物扱い | 他人の受注を見せる | 統合しない。顧客コード＋候補一覧で人が選ぶ |
| A550 と法人の混同 | PCM／法人オペ混乱 | 法人検索は App88、店舗個人は App96／PCM のまま |
| App16 受注登録の回帰 | 採番・LOOKUP・PCM 破損 | 登録UIは独立JS、saiban／LOOKUP非改変、限定動作確認 |
| `like` 性能（将来増） | 遅延 | まず顧客コード必須絞り。必要なら正規化キー＋索引戦略 |
| ふりがな空の過去データ | かな検索が当たらない | 過渡期は漢字併用＋問い合わせ時に埋める運用 |
| 空白スペース／CSS競合 | フォーム崩れ | App88 中心実装で App16 フォーム侵襲を最小化 |
