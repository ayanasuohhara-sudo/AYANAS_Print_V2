## 7. 一括入庫（全件成功）と更新失敗時の復旧（JS 実装方針）

フォーム作成時点では JS 未登録。以下は **実装・運用設計の確定** として記載。

### 7.1 一括入庫の実行条件

- ヘッダー `inbound_status` = **`下書き`**
- サブテーブルが **1行以上**
- **すべての行** で `line_result` = **`待機`**
- **`line_result` = `エラー` の行が1件でもあれば実行しない**
- 実行前に `message_space` にエラー一覧を表示し、**行の削除** または **再スキャン（原因解消）** を促す

### 7.2 更新順序（1行あたり・推奨）

kintone は **アプリ間トランザクションなし** のため、次の順で **行ごと** に処理し、失敗した時点で **処理を中断** する。

1. **出庫側**（区分に応じて）  
   - 海外: App **28** … `overseas_in_date`, `overseas_status` = `全戻り`  
   - 国内: App **27** … 該当 `outsource_detail` 行の **`line_in_date`**  
2. **受注**: App **16** … `process_status`, `location_status`, `outsource_in_date` または `overseas_in_date`

同一出庫レコード（27）に複数行がある場合、**16 更新は行ごと**、**27 の状況 `入庫` は全行 `line_in_date` 完了後** に1回。

### 7.3 途中失敗時の状態（入庫管理側）

| フェーズ | 入庫管理レコード | 明細行 |
|----------|------------------|--------|
| API 途中失敗 | `inbound_status` = **`下書き` のまま** | 原則 **`待機` のまま**（`確定成功` にしない） |
| 記録 | `inbound_remarks` に **処理ログ**（後述 §7.6） | `applied_at` は **行が完全完了したときのみ** セット |
| UI | `message_space` に中断理由・再実行案内 | — |

**禁止**: 途中失敗後に **明細をすべて削除して最初からスキャンし直す** ことを **唯一の復旧手段** にしない（§7.4 の **補完再実行** を必須とする）。

---

### 7.4 再実行（補完モード）— JS 実装条件（確定）

一括入庫で App **16 / 27 / 28** の **一部だけ更新された状態** で API エラーになった場合、**同じ入庫管理レコード** に対し **もう一度「一括入庫」** できる。  
このとき **最初から全 PUT を繰り返さない**。各行ごとに **最新状態を GET し直し**、**不足している更新だけ** を行う。

#### 7.4.1 再実行前の共通処理

1. ヘッダーが **`下書き`** であること
2. 全明細が **`待機`**（`エラー` 行があれば §7.1 どおり実行不可）
3. **`inbound_batch_no`** が空なら **新規発行**、既に入っていれば **同じ番号を維持**（同一入庫セッションの識別子）
4. 処理開始時に **入庫管理レコードを 1 回保存**（`inbound_batch_no`・ログ追記を確定）
5. **各行**について、少なくとも次を **API で再取得**:
   - App **16**（`order_record_id` / `manage_no`）
   - App **27** 出庫レコード（国内外注時・`source_outbound_record_id`）— サブテーブル **`outsource_detail`** 含む
   - App **28** 出庫レコード（海外外注時）
   - 入庫管理 **当該行**（`line_result`, `applied_at`, スナップショット列）

#### 7.4.2 行ごとの「目標状態」（このレコードの `inbound_date` を `D` とする）

| 区分 | 出庫側（先） | App 16（後） |
|------|-------------|--------------|
| **海外外注** | App **28**: `overseas_in_date` = **D**、`overseas_status` = **`全戻り`** | `process_status` = **`外注戻り`**、`location_status` = **`本社`**、`overseas_in_date` = **D** |
| **国内外注** | App **27** 該当行: **`line_in_date`** = **D**（同一行の `manage_no` 一致） | 上記に加え **`outsource_in_date`** = **D** |

App **27** レコードヘッダー **`ドロップダウン_0`**: 当該出庫レコードの **`outsource_detail` 全行** で `line_in_date` = **D** のとき **`入庫`**（未完了行があれば変更しない）。

#### 7.4.3 補完ロジック（行ループ）

各行について **出庫側 → App 16 → 27 ヘッダー状況** の順で、**目標を満たしていれば PUT をスキップ**。

```
出庫側が目標どおり → スキップ（二重更新しない）
App 16 が目標どおり → スキップ
27 ヘッダー状況が目標どおり → スキップ
すべて満たす → 当該行 line_result = 確定成功, applied_at = 現在
```

**1 行でも PUT が必要**なら実行。**API 失敗**ならそこで中断し §7.3 と同様にログ残し **下書き維持**。

**全行**が `確定成功` になった時点で初めて: ヘッダー `inbound_status` = **`確定済`**、`confirmed_at` セット。

#### 7.4.4 「通常の二重入庫」と「途中失敗の一部更新済み」の区別

| 種別 | 判定の目安 | 入庫管理での扱い |
|------|-----------|------------------|
| **A. 通常の二重入庫** | スキャン時または実行前: App 16 / 28 / 27 行が **既に別入庫として完了** しており、**今回の `inbound_date`（D）と一致しない**（日付が違う、または工程・保管場所が「入庫完了」状態なのに D と無関係） | 明細 **`line_result` = エラー**、`error_message` = **「既に入庫済み」** 等。**一括入庫不可** |
| **B. 途中失敗の一部更新済み** | ヘッダー **`下書き`**、当該行 **`待機`**、かつ **一部フィールドだけ** が **すでに D どおり**（例: 28 だけ `overseas_in_date`=D、16 は未更新） | **エラーにしない**。§7.4.3 で **不足分のみ PUT** |
| **C. 同一 D で既に全目標達成** | 再 GET で出庫・16 とも目標どおりだが、入庫管理行だけ **`待機`** のまま | **PUT スキップ**し、行を **`確定成功`** に更新（**状態の同期**） |

**区別のためのルール（実装）**

- 比較は常に **ヘッダー `inbound_date`（D）** と **当該 `manage_no`** を基準にする。
- **「既に入庫済み」エラー**は、**目標状態が D で完全に満たされている** かつ **入庫管理が別の確定済レコードで処理済み** と判断できる場合、または **日付が D 以外で完了している** 場合に限る（B/C には該当させない）。
- **B** は **`inbound_batch_no` と同一セッション**（下書き・同一レコード・`inbound_remarks` ログに `interrupted` あり）で起きた部分更新を前提とする。

#### 7.4.5 スキャン時（一括入庫前）の再判定

スキャン追加時も **GET した現状態** で A/B を判定する。

- **A** → 即 **`エラー`**
- **B に該当しそう**（下書きレコードへの再スキャンでなく、**別日付で半端な状態**）→ 原則 **A** 扱いまたは管理者確認メッセージ（実装時にメッセージを固定）
- 新規スキャンで **未入庫** → **`待機`**

### 7.6 手動復旧（最終手段）

補完再実行 **2 回以上失敗** した場合のみ、管理者が App 16/27/28 を手修正。  
入庫管理レコードは **`取消`** または明細削除後に **`下書き`** 維持。手修正後 **同レコードで補完再実行** を試みる。

**確定済**レコードは原則変更不可。
