## 1. App97 既存引き渡し処理の共通利用可否

### 1.1 現状コード

| 関数 | ファイル | 役割 |
|------|----------|------|
| `loadByBarcode` | `store_payment_api.js` | manage_no → 受注＋同一 PCM の未納品済一覧 |
| `getOrderBalance` / `canPickupWithBalance` | `store_payment_engine.js` | 入金済判定・引き取りゲート |
| `buildPickupPutRecord` | 同上 | `{ delivery_status: 納品済, delivery_date? }` のみ |
| `completePickup(orderRecordId)` | `store_payment_api.js` | GET → 残高ゲート → PUT（revision） |
| `isPickupAlreadyDone` | engine | `delivery_status === 納品済` |

`completePickup` は **入金処理（registerPayment）を呼ばない**。入金と引き取りは分離済み。

### 1.2 そのまま App92 から使えるか

**不可（現状のまま）**。理由:

1. `store_payment_*` は **App97 のカスタマイズにだけ**登録されている  
2. App92 の読込は `store_deadline_config → engine → desktop` のみ  
3. kintone はアプリごとに JS を分離するため、App97 の `window.CAYANAS_StorePayment_*` は App92 画面に存在しない

### 1.3 共通化の選択肢

| 案 | 内容 | 評価 |
|----|------|------|
| **A. 共有バンドルを App92 にも登録** | App92 に `store_payment_config/engine/api`（UI・numbering 除く）を追加読込 | 実装が早い。App97 入金コードは触らない（読込のみ） |
| **B. 共通モジュール切り出し** | `store_pickup_shared.js` に barcode解決・残高・PUT を抽出。App92/97 双方から利用 | **推奨**。関心・重複防止ロジックを一箇所に |
| **C. App92 に PUT だけ複製** | 残高判定を再実装 | 非推奨（二重メンテ・判定ずれ） |

**注意**: 現行 `completePickup` は依頼の更新条件（完了・店舗・引き取り待ち・delivery_no）を **まだ見ていない**。共通化するなら **ゲート強化版**を共有関数にし、App97 側は後方互換（既存条件＋強化）にするか、App92 専用ゲートを前段に置く。

## 3. App16 `delivery_status` に「引き取り待ち」追加の影響

### 3.1 現状オプション（本番 fields バックアップ）

| 値 | index |
|----|-------|
| 未納品 | 0（既定） |
| 納品待ち | 1 |
| 納品済 | 2 |

**「引き取り待ち」は存在しない。** 追加は App16 フォーム変更（別承認）が必要。

### 3.2 現行の書き手

| タイミング | 設定値 | コード |
|------------|--------|--------|
| App30 完了登録 | **納品待ち** | `complete_register_engine` |
| App19 A550 納品書 | **納品待ち**（＋delivery_no） | `delivery_complete_sync` |
| App19 法人納品書 | **納品済**（＋location=納品済） | 同上・法人経路 |
| App97 引き取り | **納品済** | `buildPickupPutRecord` |

### 3.3 影響マトリクス（追加した場合）

| コンポーネント | 現状の見方 | 「引き取り待ち」追加時の必要な対応 |
|---------------|------------|-------------------------------------|
| App92 納品待ち在庫 | `delivery_status=納品待ち` ∧ delivery_no ∧ 店舗 ∧ 完了 | **どちらを在庫表示するか再定義**（納品待ちのままか、入金後の引き取り待ちか） |
| App92 スケジュール除外 | 納品済 **または** delivery_no 非空 | 引き取り待ちでも delivery_no ありなら既に除外（追加影響小） |
| App92 KPI「完了・納品待ち」 | process=完了 ∧ delivery=納品待ち | 引き取り待ちを含める/除外する方針が必要 |
| App97 未精算クエリ | `delivery_status not in (納品済)` | 引き取り待ちは未精算一覧に **残る**（意図どおりならOK） |
| App97 completePickup | 納品済なら alreadyDone | 引き取り待ち → 納品済は現行でも動く。ゲート強化は別途 |
| App30 / App19 A550 | 納品待ちを書く | **誰が「引き取り待ち」に遷移させるか**が未定義だとオプションが死ぬ |

### 3.4 状態遷移の未決事項（要承認）

依頼の更新条件は `delivery_status = 引き取り待ち`。しかし現状フローでは入金後も **納品待ちのまま** App97 が直接 **納品済** にしている。

```text
現状:
  完了(納品待ち) → 納品書(納品待ち+no) → [入金] → App97引き取り(納品済)

依頼イメージ:
  … → (納品待ち+no) → [入金] → 引き取り待ち → App92バーコード(納品済)
```

| 案 | 遷移 | メリット | デメリット |
|----|------|----------|------------|
| **P1（フィールド追加＋遷移追加）** | 入金完了時または App97 側で `納品待ち→引き取り待ち`、App92 で `→納品済` | 依頼条件どおり。店舗では「支払い済みだけ掃く」 | App97 または別トリガーの変更が必要（「App97入金処理を変えない」と緊張） |
| **P2（フィールド追加のみ・手動/別JS）** | 店舗責任者が状態を引き取り待ちへ | App97 非変更 | 運用負荷・抜け漏れ |
| **P3（フィールド追加しない）** | App92 の対象を現行「納品待ち∧店舗∧完了∧delivery_no∧入金済」に | フィールド変更不要・最短 | 依頼の文言「引き取り待ち」とは不一致 |

**調査上の推奨**:  
- 依頼文言を厳密に守るなら **P1**。ただし「App97 入金処理を変更しない」制約があるため、**入金 registerPayment は触らず**、引き取り前の状態更新を **別イベント**（例: 入金成功後の薄いフック、または App92 読取時に入金済なら実質ゲート）にする必要がある。  
- リスク最小化なら **P3 で先行実装**し、ラベル上「引き取り対象＝入金済みの納品待ち在庫」とし、フィールド追加は第2弾。

いずれにせよ **法人の delivery/location=納品済 経路は触らない**。

## 4. 入金済み・未入金・一部入金の判定

正本は App97 S1（変更せず参照）:

```text
billedInclusive = round(ΣApp16明細税抜 × 1.1)   // 受注単位
paid            = Σ(有効な App97 明細の allocated_amount)  // 取消除外、返金は負
balance         = billedInclusive - paid

state:
  未入金   … paid == 0
  一部入金 … paid > 0 かつ balance > 0
  入金済   … balance <= 0 かつ billed > 0
  過剰入金 … paid > billed
```

引き取りゲート（現行）:

- `balance <= 0` → 可  
- 一部/未入金 → 不可（`unpaidHandoverApproved` 例外あり）

App92 バーコード引き取りでも **同じ関数を共有**すべき。独自再実装は禁止推奨。

## 6. 二重引き取り・誤読取・混入防止

| リスク | 対策（案） |
|--------|------------|
| 二重引き取り | `delivery_status=納品済` なら alreadyDone。PUT に `$revision`。競合時再GET |
| 未条件の更新 | ゲート: A550 ∧ 完了 ∧ 店舗 ∧（引き取り待ち **または暫定で納品待ち+入金済**）∧ delivery_no 非空 |
| 他お客様混入 | カート先頭の PCM / client と不一致なら追加拒否 |
| 誤読取（存在しない番号） | manage_no 0件/複数件はエラー停止（App19同期と同型） |
| 未入金の誤完了 | `canPickupWithBalance` 必須。管理者例外は明示トグル＋確認 |
| 工場在庫の誤完了 | `location_status=店舗` 必須 |
| 納品書未作成 | `delivery_no` 必須 |
| 法人誤操作 | `customer_code=A550` 以外は読取時点で拒否 |
