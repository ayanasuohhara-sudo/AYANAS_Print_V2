## 3. 完了登録時の App16 ステータス（4軸）

`buildCompletePutRecord`（完了登録のみ）が更新するフィールド:

| フィールド | 値 | 備考 |
|------------|-----|------|
| `process_status` | **完了** | 工程軸 |
| `work_status` | **仕上げ完了** | 作業軸 |
| `delivery_status` | **納品待ち** | 納品軸。**納品済にはしない** |
| `completion_date` | 当日 | |
| `location_status` | **変更しない** | 場所軸は完了登録のみでは触らない |

注意（要件との整合）:

- 「店舗に現物があること」と「工程完了」は分離されている（location を勝手に店舗にしない）
- 納品済化は App19（法人）／App92・97 引き取り側。App30 は納品待ちまで

## 6. 追加が必要な機能（任意・優先度順）

コア運用は現状で開始可能。改善するなら:

| 優先 | 内容 | 変更候補 | 影響 |
|------|------|----------|------|
| P2 | 一覧に **商品名**（明細先頭 `item_name` 等）を追加 | `complete_register_engine.js`（取得フィールド）／`complete_register_desktop.js`（列） | UI のみ。PUT 非変更 |
| P2 | ボタン文言を「一括完了登録」に（または併記） | `complete_register_desktop.js` | 文言のみ |
| P3 | Enter 無しスキャナ（入力デバウンス） | desktop（App34 `location_inbound_desktop` と同様） | 読取UX。法人フロー非破壊 |
| P3 | App16 側 manage_no 重複（limit 2）を読取時検知 | desktop `fetchOrder` | データ品質。稀 |

**やらない方がよいこと**

- 完了時に `delivery_status=納品済` にする（要件違反・法人／引き取りと衝突）
- 完了時に location を店舗へ強制（現物と工程の混同）
- A550 専用の別完了アプリを新設（既存流用で足りる）

## 7. 実装方法（もし改善する場合）

1. **既存を拡張**する（新規アプリ不可）
2. PUT 正本は引き続き `complete_register_engine.buildCompletePutRecord` のみ
3. 商品名列追加時も `process` / `work` / `delivery` / `location` の更新マトリクスは変えない
4. 単体: `scripts/test_complete_register_engine.js` を維持・追加
5. 本番反映は **別承認後**（本調査では実施しない）

法人経路: App30 は顧客種別を見ないため、列追加・文言変更だけでは法人完了処理は壊れない。エンジンの PUT キーを増やさない限り 4 軸契約も維持できる。
